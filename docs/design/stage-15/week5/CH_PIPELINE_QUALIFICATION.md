# CH pipeline: one-stage native qualification

**Prepared; not executed.** This procedure qualifies the delivered merge,
position-sample and history-index adapters. It leaves every delivered source,
design and earlier proof byte-identical. It grants no human source execution,
engine scoring, scientific inference or release of the 44 prospective cells.

## DESIGN CHECK

LESSONS 2–5 and [the delivered adapter design](CH_PIPELINE_BOUNDED.md) govern.
The case is whether a counted native attempt can stop after actual source work,
copy its whole authenticated checkpoint into a new attempt, stop during actual
independent verification, and finally verify from source zero with exactly the
original scientific outputs. The check uses the original 576-game constructed
source and original implementations, both native process boundaries, full
checkpoint manifests, native exits, released leases and actual watcher records.
The smaller route is to retain a failure or external interruption and stop the
sequence for review. There is no automatic retry or reduced scientific test.

## Immutable inputs and stage order

The controller pins the delivered preparation manifest and every file it names,
the actual complete source closure, current reviewed runtime/launcher, the new
qualification sources and native foundation receipts supplied by the owner.
Both this note and the delivered adapter note must match the actual reviewed
Git commit. Reading that commit does not stage, commit or publish anything.

The sequence has ten separately launched counted attempts:

1. Complete the delivered constructed original-output fixture, with its full
   independent native replay and source/tamper refusals.
2. Merge execution pilot; merge verification pilot in a new attempt; complete
   merge verification in a third attempt.
3. Position-sample execution pilot; sample verification pilot in a new attempt;
   complete sample verification in a third attempt.
4. History-index execution pilot; index verification pilot in a new attempt;
   complete index verification in a third attempt.

All three chains take the same immutable constructed inputs from the first
counted fixture. This makes comparison with its frozen original outputs exact,
including the history index's physical source-file checksum. It is a separate
runtime qualification of each adapter; it does not claim that newly scheduled
human pipeline dependencies have been admitted. The final component checks
compare all original scientific merge tables, original selected-player JSON,
position gzip bytes, source counts, history payloads/settings and index receipt.
Operational SQLite tables are not substituted for scientific content equality.

`fixture_passed` in the initial native plan refers to the owner's already passed
parser/runtime foundation receipts, not to this unrun adapter qualification.
The first fixture supplies a complete counted reference before any continuation
chain is admitted. Its completion and every bound artifact are pinned in the
later plans, not just the top-level marker.

## Deterministic actual pilot pauses

The separately named constructed-only wrapper invokes each delivered adapter
unchanged. Its process-local progress subclass observes the already committed
transaction boundary and raises a qualification pause after the first available
nonterminal transaction crossing five percent of fixture work. It restores the
original progress class on every exit. The delivered code files, source
selection, numerical fields, comparisons and independent verification are not
changed. No synthetic owner message or invalid watcher envelope is written.

The fixture is small, so transaction granularity may put a pause substantially
after five percent. Every receipt reports the actual numerator, denominator and
fraction; this is not called an exact five-percent sample or a full-source cost
pilot. Native fixture allowances are below 7,200 CPU seconds. The campaign's
separate first-five-percent cost rule for large scientific work remains intact.

The first native attempt pauses during execution. The second uses the actual
runtime's complete sealed copy, finishes execution, then pauses during the
independent verifier's first pass. The third again uses the complete sealed copy;
execution recognizes its completed seal and verification recomputes from source
ordinal zero. Copied execution or verification prefixes receive no verification
credit. Both pilot receipts remain in the copied output. The runtime manifest
excludes only its documented transient progress/request files and temporary
files; every other checkpoint artifact is copied and hash-checked. A resource or owner
interruption outside the intended pilot is retained as such and does not pass
the stage or silently alter the next stage's role.

## One stage per owner action

The controller has four commands: `init`, `launch`, `inspect` and `finalize`.
`launch` requires an explicit stage name and starts exactly one native counted
attempt, then returns. It never waits in a poll loop, fills a slot later or
launches the following stage. The existing durable watcher owns terminal
delivery. After delivery, `inspect` checks that exact stage. A later explicit
`launch` requires the preceding inspected stage to have passed.

Inspection requires exact owner/plan binding; native owner, launcher-child and
actual-child identities absent by creation-time identity; released lease;
actual watcher identity registration and valid terminal schema; zero native
exit codes; descendant accounting receipts; reconciled terminal CPU; and exact
full checkpoint/output hashes. A terminal written while the owner is still
exiting is reported as pending, without declaring a failure or starting a job.
Snapshots of all predecessor files are retained outside the attempts and checked
again before continuation and finalization. Repeating an already completed
inspection only validates and returns the prior immutable inspection.

Unknown/missing accounting, ambiguous terminals, changed predecessors, unexpected
pauses, failed parity or a failed fixture stops advance. No file is deleted,
no process is killed, and no failed attempt is reused. Recovery requires an
owner-reviewed new sequence or successor, preserving these attempts.

## Proposed bounds and evidence

The reference fixture has a proposed 600-CPU-second combined execute/replay cap
and 1,800-second wall cap. Each of the nine continuation attempts has 300 CPU
seconds and 1,200 wall seconds. Each uses two numerical threads, at most 2 GiB
projected peak RAM and a 2 GiB output cap. The full ten-attempt CPU envelope is
3,300 seconds, not a measured forecast or reservation. All actual failed and
successful attempts are charged to CH. Each start rechecks the active window,
family room, shared-resource limits and currently free counted slot. No
authorization to increase those caps or restart parked work is inferred.

The final proof retains per-attempt measured descendant CPU, measured controller
process CPU and explicit conservative allowances of 30 CPU seconds per native
supervisor, five per native-launch shell, and one per controller command tail.
These allowances are labelled separately from measurements. It binds every
inspection and the reviewed source closure, and leaves scientific admission
false. The owner performs internal write-through and watcher acknowledgements;
this driver does neither.

No command has been executed, no tests have run, and no native job has started
under this preparation. The next authorized action is owner review of the exact
new source and design, followed by a separately authorized first counted stage.
