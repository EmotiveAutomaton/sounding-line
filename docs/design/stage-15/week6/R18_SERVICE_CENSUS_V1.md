## Findings from bounded read-only inspection

The durable watcher is the exact `tools/codex_watch.py run` process. Its run path
scans final produces, checks native disappearance, keeps notification state and
submits existing-owner operational messages. It does not import scientific
handlers or call accounting, budget or admission functions. `register-queue`
can inspect queue code, but is a different CLI command and is never exempted.
Its startup record retains the watch/common/queue-transport hashes; all three
match current bytes. The native identity implementation is separately pinned
and predates the observed process. The run path imports no other local module.

The calendar's exact implementation remains the already reviewed clock-only
source. Windows keeps its virtual-environment launcher alive as the actual
interpreter's direct parent. The launcher's command equals the child's command,
and its creation precedes the child by less than a second. The old census
exempts only OWNER's interpreter identity, then wrongly refuses this parent.
The same forwarding parent can exist for the census caller itself and for
already owned new attempts. Parentage is not inferred from a PID alone.

The private observation records exact native identities, commands, startup
pins and binary hashes. It contains no human data or scientific estimates.
It is an observation, not an indefinite liveness guarantee. A transient Codex
hook was also observed. It is not a durable accounting service and has a wider
lint/notification dependency closure; this proposal does not grant it an
exception. Wait for it to finish or review a separate exact proof. Other-project
processes retain the existing outside-workspace treatment and are never stopped.

## Additive changes

`week6_process_services_v1` provides the read-only identity checks. The watcher
exception requires one exact service kind, owner review, fixed code/image pins,
the exact `pythonw -B <watcher> run` argument vector and repository cwd, the
unchanged recorded startup binding, source times predating native creation,
and an exact current native/command/cwd match. SQLite opens in read-only mode;
the watcher's status CLI is not invoked. A stopped watcher contributes no
allowed identity. A reused PID or changed source cannot inherit the exception.

Only a pinned native venv launcher can be added as the parent of an already
authenticated interpreter or the current reviewed caller. It must be the
observed direct parent, run the identical full command and cwd, have the exact
reviewed venv/base executable paths and hashes, and precede that child by at
most five seconds. This is a C forwarding process, not arbitrary Python code.
Native identity is sampled before and after reading command/cwd/parent. Errors
remain errors; a no-such-process exception also needs native absence. Binary
pins are checked again after the census. No child or unrelated ancestor gains
authority from being related to an allowed process.

`week6_transition_services_v1` preserves the complete original legacy inventory,
terminal/exited proof, calendar proof, immutable budgets, source closure and
full-filing requirements. Its new review schema adds `compatible_services`
and `python_forwarder_images`. Exact new OWNER/child bindings retain their
existing role. The command-only pre-OWNER exception is removed: an unfamiliar
runtime with a plausible module name and frozen root still refuses.

This conservative handshake rule fits the actual runtime: it writes OWNER
before the first budget-reading slot claim. Its paired C launcher is then
recognized from that exact owner. The current caller's paired launcher can be
recognized before OWNER because the caller is already executing the reviewed
guard. Concurrent unrelated pre-OWNER starts must settle before the next
admission. Serialize ordinary launches and verify OWNER/MONITOR_READY; do not
silently ignore or stop an unowned process. No new launch tickets are invented.

The policy, generic runtime, monitored launcher and TR2 source runtime have
separately named additive successors selecting the new transition/policy. Their
accounting epoch remains `week6-extension-v2`. Existing limits, inclusive Job
accounting, failures, original allowance modes, families, 6,000,000 campaign
ceiling, two threads, eight slots, clocks, memory/disk guards and monitoring
remain byte-for-byte apart from module selection. The unchanged limits module
remains inherited. Every old and new required reader source is pinned.

The frozen carried migration candidate still selects the earlier extension
policy. It requires a separately reviewed additive integration before using
this successor. Do not edit or install its frozen files to work around that
dependency. Historical and shared preparation attribution remains held exactly
as previously delivered; this census repair does not settle or reset costs.
